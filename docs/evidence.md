## E1. Выпущенный Orthrus обучает Q, K, V **и O**, а не только Q, K, V

*3 октября 2026.*

**Утверждение.** В весах `chiennv/Orthrus-Qwen3-1.7B` двойник выходной проекции
`o_proj_diff` обучен так же сильно, как q/k/v. Раздел 3 статьи
(arXiv 2605.12825) называет обучаемыми только `W_Q, W_K, W_V`.

**Доказательство.** Двойники инициализируются копией AR-весов
(`copy_diff_from_ar` в их коде), поэтому необученный двойник совпадает с
оригиналом. Средний относительный сдвиг `‖W_diff − W‖ / ‖W‖` по 28 слоям:

| Двойник | Сдвиг |
|---|---|
| q_proj_diff | 0.318 |
| k_proj_diff | 0.352 |
| v_proj_diff | 0.315 |
| **o_proj_diff** | **0.341** |
| q_norm_diff | 0.001 |
| k_norm_diff | 0.002 |

**Это полное обучение, а не LoRA**, хотя в их `config.json` есть поля `r: 16`
и `lora_alpha: 32`. У LoRA ранга 16 разность весов лежала бы в 16 направлениях.
Здесь 90% её энергии набирается только на ~900 из 2048 направлений, а на
16 главных приходится 8–14%.

**Независимая проверка по их же тексту.** Статья пишет «около 16% параметров».
Для Qwen3-8B (скрытый размер 4096, 36 слоёв, 8 KV-голов по 128):
- только Q, K, V — 0.91B обучаемых из 9.1B, **10%**;
- Q, K, V и O — 1.51B из 9.7B, **16%**.

Для 1.7B у нас при перекладке вышло 357.6M из 2.08B, 17%.

**Воспроизвести.** `PYTHONPATH=. python tools/import_orthrus.py chiennv/Orthrus-Qwen3-1.7B out.ckpt`.
Вывод: [results/orthrus-release-1.7b-import.txt](../results/orthrus-release-1.7b-import.txt).

**Следствие.** Наша ветка `qwen06_orthrus` (Q, K, V) соответствует тексту
статьи, но слабее выпуска на целую проекцию. Её правильное название —
«Orthrus по описанию статьи», не «как опубликован». Для пары с выпуском
добавлен `qwen06_orthrus_qkvo` (сравнение C10).

## E3. Наша обвязка декодирует их веса так же, как их собственный код

*3 октября 2026.*

**Утверждение.** Переложенные в наш формат веса дают в нашем `generate` тот же
текст и ту же поцикловую приёмку, что `generate` из их `modeling_orthrus.py`.
Расходится только учёт на границе лимита токенов (E7).

**Доказательство.**
1. Поцикловая сверка: 6 промптов (gsm8k и humaneval по 3), 64 токена, `float32`.
   Текст совпал токен в токен во всех шести. Поцикловые последовательности
   совпадают до входа в последние 32 токена лимита. Пример (gsm8k #0, совпадает целиком):
   ```
   их:   [8, 0, 4, 3, 6, 1, 4, 5, 6, 1, 3, 2, 8]
   наши: [8, 0, 4, 3, 6, 1, 4, 5, 6, 1, 3, 2, 8]
   ```
2. Один проход драфтера двумя реализациями на одном и том же состоянии:
   18 состояний, 558 позиций, наибольшее `|Δ log p|` = 8·10⁻⁶, argmax не
   разошёлся ни разу.

**Воспроизвести.** `tools/orthrus_xcheck.py`, `tools/orthrus_logits_check.py`.
Вывод и разбор: [results/orthrus-release-1.7b-xcheck.txt](../results/orthrus-release-1.7b-xcheck.txt).

**Следствие.** Разрыв между нашим Orthrus (приёмка ≈ 2.2 на 0.6B) и их
(≈ 5–6 на 1.7B на тех же промптах) — это обучение, а не обвязка замера.

## E6. Разрыв со статьёй не объясняется длиной генерации

*3 октября 2026. Сравнение C6.*

На одних и тех же 180 промптах переход от 64 к 512 токенам (в среднем 345,
ответы заканчиваются раньше) поднимает приёмку Orthrus при одном проходе на
**+0.110 ± 0.074**, FlowDraft — на **+0.119 ± 0.087**. На MATH-500 у нас 2.52
против их 11.7 на 8B. Длина замера из списка объяснений вычеркнута.

Попутно: на AIME, где генерация упирается в лимит 512, приёмка с длиной
**падает** у обеих моделей (qkv при n4v: 4.50 → 4.01). Гипотеза, не
проверенная: модели учились на контексте 256.

## E7. Учёт последнего цикла у нас и у авторов различается

*3 октября 2026.*

Наш цикл всегда драфтит полный блок из 31 позиции. Принятое сверх
`max_new_tokens` обрезается после проверки, но в `acceptance` засчитывается.
Их цикл в последних 32 токенах лимита укорачивает блок до остатка
(`diff_len = min(block_size, max_length − start_idx)`).

Это различие в определении, а не ошибка. Но из него следует:
- наше `acceptance` на коротких генерациях чуть завышено относительно их
  определения (обе наши ветки одинаково, контрасты не страдают);
- со статьёй сравнивать по `tpf`, где последний цикл учтён честно.

Связано с известным смещением `tpf_steady` на один проход за генерацию
(+1.6% при 64 токенах).

## E8. Как усредняют таблицы README

Таблицы README — невзвешенное среднее по шести наборам; столбец «tokens per
forward» — `tpf_steady`. Пример, 80k, n1: среднее наборов A = 2.201 (Orthrus) и
2.576 (qkv), среднее по 460 промптам — 2.169 и 2.529. Контрасты в README —
среднее по промптам, и они совпадают с `tools/paired.py` до третьего знака.

## E10. Лишние проходы драфтера не окупаются по скорости — у нас и у авторов

Условие окупаемости `(n+1)`-го прохода: `A(n+1) − A(n) > TPF(n)`. На 80k оно
не выполняется ни на одном переходе ни у одной ветки: TPF FlowDraft падает
1.788 → 1.422 → 1.185 → 1.038 (n1 → n4v). В таблице 3 статьи двухпроходный
вариант даёт 3.53 против 6.35 у однопроходного — тот же вывод.

Выигрыш многошагового **обучения** при одном проходе при этом есть: n1,
+0.360 ± 0.035 принятого токена против Orthrus (C3).
